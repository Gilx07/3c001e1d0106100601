Memahami Perilaku dan Cara Mendeteksi Program Cheat Point Blank V1

26 Agustus 2026Windows / PE32 / Detection Engineering / Anti-Cheat

Executive overview

Tulisan ini merupakan rilis teknis lengkap dari analisis statis terhadap tiga artefak PE32/x86 yang berkaitan dengan sebuah program cheat Point Blank V1. Sasaran utamanya adalah developer game, anti-cheat engineer, detection engineer, incident responder, dan analyst yang membutuhkan indikator konkret untuk membedakan perilaku normal dari pola process injection, thread-context manipulation, hardware breakpoint, Vectored Exception Handler (VEH), perubahan memory protection, serta modul yang menyamarkan format aslinya.

Binary tidak dijalankan selama tahap analisis ini. Karena itu, setiap kesimpulan dipisahkan menjadi terkonfirmasi secara statis, sangat kuat tetapi belum runtime-validated, atau hipotesis yang masih memerlukan telemetry/debugging terisolasi. Pemisahan ini penting agar indikator tidak berubah menjadi asumsi yang berisiko menghasilkan false positive atau tindakan enforcement yang tidak proporsional.

Tujuan publikasi: memberikan material yang cukup rinci agar pihak developer dapat melakukan triage, membuat telemetry, mengembangkan signature, memvalidasi runtime behavior, dan membangun mitigasi. Detail yang tidak diperlukan untuk pertahanan dan hanya berguna untuk mereplikasi mekanisme injection tidak dijadikan instruksi operasional.

1. Ruang lingkup analisis

Analisis difokuskan pada hubungan antar-artefak, primitive process injection, manipulasi thread dan context, memory protection, exception handling, hooking/redirection, komunikasi jaringan, static indicators, telemetry runtime, serta strategi validasi yang dapat digunakan pihak game.

  • Memahami peran masing-masing file dan kemungkinan hubungan di antaranya.
  • Mengidentifikasi executable yang berperan sebagai launcher/injector/controller.
  • Mengidentifikasi modul runtime yang melakukan thread-context redirection.
  • Memetakan API process access, remote allocation/write, thread manipulation, exception handling, dan networking.
  • Menyusun IOC exact-match dan static behavioral triage.
  • Menyusun event telemetry dan behavioral scoring untuk anti-cheat.
  • Mendefinisikan rencana validasi runtime yang aman dan repeatable.

Executable pertama menunjukkan kombinasi import dan call-flow yang konsisten dengan controller yang mencari proses target, membuka proses dengan hak luas, mengalokasikan memory remote, menulis data/stub ke proses target, mengaktifkan execution primitive, menunggu completion, lalu melakukan cleanup.

4. Call-flow remote process yang terkonfirmasi

Disassembly statis menemukan dua routine injection yang sangat mirip di sekitar RVA 0x25xx dan 0x29xx. Pola umumnya:

OpenProcess(access luas)
  -> resolve required function(s)
  -> VirtualAllocEx untuk path/data
  -> WriteProcessMemory untuk path/data
  -> VirtualAllocEx untuk remote stub
  -> WriteProcessMemory untuk remote stub
  -> internal helper mengaktifkan remote execution
  -> WaitForSingleObject
  -> VirtualFreeEx
  -> CloseHandle

Ini mengangkat confidence dari sekadar “memiliki API injection” menjadi memiliki implementasi remote-process injection yang benar-benar terhubung dalam call-flow.

Call-site penting untuk triage dan correlation

  • RVA 0x2680 dan 0x296C: OpenProcess dengan desired access 0x1FFFFF.
  • RVA 0x276B dan 0x29FB: penggunaan VirtualAllocEx untuk alokasi memory remote.
  • RVA 0x27EE, 0x2861, 0x2A36, 0x2A6A: WriteProcessMemory untuk path/data dan remote stub.
  • RVA 0x28CE dan 0x2A91: menunggu completion melalui WaitForSingleObject.
  • RVA 0x28DC/0x28EC dan 0x2A9F/0x2AAF: cleanup memory remote melalui VirtualFreeEx.

5. Primitive remote thread: kecocokan kuat NtCreateThreadEx

Helper internal sekitar RVA 0x24C0 tidak memanggil API thread creation melalui import table. Ia melakukan resolusi fungsi secara dinamis melalui identifier internal, mendekode ntdll.dll, lalu memanggil fungsi hasil resolusi menggunakan susunan argument yang sangat cocok dengan signature NtCreateThreadEx.

Argumen yang terlihat konsisten dengan output thread handle, desired access, object attributes, process handle, start address, parameter, flags, zero bits, stack commit/reserve, dan buffer tambahan. Dengan demikian status temuan adalah:

6. Dua jalur payload dan orchestration

Call-site RVA 0x731F dan 0x7342 memanggil dua routine injection berbeda, masing-masing menuju routine sekitar 0x2910 dan 0x2610. Sebelum pemanggilan, process identifier diteruskan melalui ECX, sedangkan pointer path diteruskan melalui EDX. Kedua routine menggunakan GetFullPathNameA sebelum menjalankan chain remote-process yang sama.

Interpretasi yang paling kuat adalah executable memiliki dua kandidat path/payload yang dicoba secara berurutan. Jika jalur pertama gagal, kode berpindah ke jalur kedua. Setelah kegagalan berulang terdapat retry delay; setelah sukses handle proses ditutup, terdapat delay pendek, lalu flag state internal di-set.

target/process discovery
  -> OpenProcess(access luas)
  -> injection path A
  -> jika gagal: injection path B
  -> jika keduanya gagal: Sleep sekitar 100 ms
  -> kembali ke outer loop
  -> outer discovery loop juga memiliki Sleep sekitar 200 ms
  -> jika sukses: CloseHandle
  -> Sleep sekitar 10 ms
  -> success state flag = 1

Pada area .rdata terdapat string case-variant PointBl dan pointbl. Ini adalah indikator kuat terhadap pencarian target, tetapi bentuk nama lengkap tidak dipaksakan sebagai fakta karena data di sekitarnya masih menunjukkan transformasi/obfuscation.

7. Remote stub: apa yang diketahui dan apa yang belum

Dua routine injection membentuk stub kecil berukuran sekitar 17 byte di stack sebelum menyalinnya ke proses target. Secara konseptual, struktur yang terlihat adalah rangkaian push terhadap parameter runtime, pemuatan function pointer ke register, indirect call, lalu return.

Placeholder dan operand runtime belum dapat dipetakan secara penuh hanya dari file mentah. Karena itu, analisis tidak menyatakan nama loader final atau path final. Yang terkonfirmasi adalah keberadaan stub remote kecil, proses penyalinan stub, dan activation primitive yang mengikuti penulisan tersebut.

8. Artefak DLL runtime: initialization dan worker

DLL besar menunjukkan profil berbeda dari executable. Entry point berada pada RVA 0x90E4C. Pada DLL_PROCESS_ATTACH, kontrol diteruskan ke dispatcher internal sekitar RVA 0x90D16, kemudian ke routine sekitar RVA 0x77FA0.

Routine initialization:

  • memanggil DisableThreadLibraryCalls;
  • membuat worker dengan start address 0x100561F0;
  • membuat worker kedua dengan start address 0x100773E0.

9. VEH dan EXCEPTION_SINGLE_STEP

Salah satu worker memasang AddVectoredExceptionHandler dengan callback pada alamat 0x10077320. Callback memeriksa exception code 0x80000004, yaitu EXCEPTION_SINGLE_STEP.

Jika exception address cocok dengan lokasi internal yang dipantau, callback mengubah instruction pointer pada context ke alamat internal lain, termasuk 0x1002FBD0 atau 0x100321A0, kemudian menandai exception sebagai handled.

hardware breakpoint fires
      |
      v
EXCEPTION_SINGLE_STEP
      |
      v
VEH callback
      |
      +--> validate exception address
      |
      v
modify instruction pointer
      |
      v
continue execution through redirected routine

10. Thread enumeration dan debug-register manipulation

Worker yang sama melakukan urutan:

  1. GetCurrentProcessId.
  2. CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD).
  3. Memfilter thread berdasarkan owner process ID.
  4. Membuka thread dengan access 0x1FFFFF.
  5. SuspendThread.
  6. GetThreadContext menggunakan ContextFlags = 0x10010.
  7. Mengubah context/debug registers.
  8. SetThreadContext.
  9. ResumeThread.

Context yang disiapkan mengandung Dr7 = 0x55. Nilai Dr0/Dr1 berasal dari state internal. Pada x86, Dr0–Dr3 dapat menyimpan alamat hardware breakpoint, sedangkan Dr7 mengontrol aktivasi breakpoint. Kombinasi ini merupakan bukti kuat bahwa mekanisme utama DLL menggunakan hardware breakpoint + VEH redirection.

11. Memory protection dan instruction-cache behavior

DLL melakukan beberapa pemanggilan VirtualProtect terhadap state/code internal dengan protection 0x40 atau PAGE_EXECUTE_READWRITE, kemudian mengembalikan protection lama. FlushInstructionCache juga terlihat pada surface runtime.

Bagi anti-cheat, perubahan executable page menjadi writable lalu executable kembali, terutama bila berdekatan dengan context manipulation atau exception redirection, merupakan sinyal bernilai tinggi. Namun sinyal ini harus dikorelasikan dengan signer/module allowlist karena JIT engine, security software, dan beberapa legitimate runtime juga dapat melakukan perubahan protection.

12. Penilaian mekanisme hook/redirection

Tidak ditemukan import/string yang cukup kuat untuk menyimpulkan modul runtime menggunakan library inline-hook tertentu. Sebaliknya, bukti yang konsisten adalah:

  • dua worker thread saat attach;
  • VEH untuk EXCEPTION_SINGLE_STEP;
  • pengaturan Dr0/Dr1/Dr7;
  • wrapper/dispatch internal dan indirect call/jump;
  • VirtualProtect dan FlushInstructionCache.

Kesimpulan defensif yang paling aman adalah custom redirection berbasis hardware breakpoint + VEH. Kemungkinan inline/IAT hook di area lain belum dapat dikesampingkan, tetapi tidak didukung sebagai mekanisme utama oleh evidence yang tersedia.

13. Artefak .ini yang sebenarnya DLL

7677826866.ini bukan file konfigurasi teks. PE header menunjukkan PE32 DLL x86 dengan:

  • entry point RVA 0x144F;
  • image base 0x10000000;
  • import utama KERNEL32.dll dan MSVCR100.dll;
  • tidak memiliki export directory;
  • resource berupa manifest asInvoker.

Disassembly entry-flow menunjukkan wrapper DLL standar MSVC, IsDebuggerPresent, SetUnhandledExceptionFilter/UnhandledExceptionFilter, callback exception internal, function pointer global, dan state lifecycle berbasis InterlockedExchange/InterlockedCompareExchange.

Tidak terlihat VirtualAllocEx, WriteProcessMemory, SetThreadContext, CreateThread, atau networking pada import table. Penilaian saat ini: modul runtime/guard/exception-support pendamping, bukan injector utama. Hubungannya dengan dua artefak lain belum terkonfirmasi.

16. Detection philosophy: sequence > single signal

Nama file, hash, satu API, atau satu memory-protection event tidak cukup sebagai dasar enforcement. Detection engineering yang kuat menggabungkan:

static IOC
   + signer/path reputation
   + process access telemetry
   + remote memory telemetry
   + thread/context telemetry
   + module/VEH telemetry
   + server-side session context
   = correlated confidence

Sequence bernilai tinggi dalam window sekitar 30 detik:

process discovery
  -> external OpenProcess(access luas)
  -> VirtualAllocEx
  -> WriteProcessMemory
  -> remote thread or context modification
  -> unknown module / VEH / hardware breakpoint

17. High-value indicators untuk pihak game

  • Proses eksternal memperoleh handle game dengan PROCESS_VM_OPERATION, PROCESS_VM_WRITE, PROCESS_CREATE_THREAD, atau access sangat luas.
  • VirtualAllocEx diikuti WriteProcessMemory terhadap proses game.
  • Remote execution dengan start address pada private/executable memory.
  • Thread game di-suspend lalu diakses melalui GetThreadContext/SetThreadContext.
  • ContextFlags = 0x10010 pada context manipulation yang tidak berasal dari tool resmi.
  • Dr0–Dr3 non-zero atau Dr7 = 0x55 pada thread game.
  • VEH tambahan dari modul tidak resmi yang menangani EXCEPTION_SINGLE_STEP.
  • Executable page berubah menjadi writable/executable, terutama disusul FlushInstructionCache.
  • Module tidak ditandatangani, path user-writable, nama acak, atau ekstensi file tidak cocok dengan PE header.
  • Case-variant process discovery seperti PointBl/pointbl yang diikuti chain injection.
  • Retry sekitar 100 ms setelah kegagalan injection dan discovery loop sekitar 200 ms sebagai timing indicator tambahan.
  • WinINet activity dari module yang tidak dikenal atau tidak ditandatangani.

18. Event telemetry minimum

Untuk deteksi awal, sensor tidak perlu menyimpan isi memory game atau data pribadi. Metadata operasi sudah cukup bernilai:

{
  "timestamp": "2026-08-25T00:00:00Z",
  "source_pid": 1234,
  "target_pid": 5678,
  "source_image_sha256": "...",
  "source_path_class": "user-writable|program-files|unknown",
  "operation": "open_process|remote_alloc|remote_write|remote_thread|thread_context|module_load|veh_observed",
  "requested_access": "0x1fffff",
  "memory_protection": "0x40",

Tambahkan parent process, image base, signer identity, start time, target module, dan session identifier bila tersedia. Data tersebut memungkinkan korelasi tanpa mengambil gameplay data atau memory contents secara default.

19. Behavioral scoring baseline

Baseline berikut bukan kebijakan ban; ini titik awal untuk calibration:

  • +100 exact SHA-256 artefak terkonfirmasi.
  • +25 unsigned/unknown module dengan ekstensi palsu.
  • +25 external process membuka game dengan access luas.
  • +25 VirtualAllocEx terhadap game.
  • +35 WriteProcessMemory terhadap game.
  • +35 remote execution primitive atau start address pada private memory.
  • +35 suspend thread lalu Get/SetThreadContext.
  • +40 debug register non-zero pada thread game.
  • +35 VEH EXCEPTION_SINGLE_STEP dari module tidak resmi.
  • +20 executable page menjadi writable kemudian executable.
  • -30 satu sinyal tunggal dari software resmi yang ditandatangani.
0–39   : observation
40–69  : review + additional telemetry
70–99  : high-confidence investigation
100+   : containment/review according to developer policy

Auto-ban berdasarkan skor client tunggal tidak direkomendasikan. Simpan event sequence dan korelasikan dengan server-side evidence sebelum tindakan akun permanen.

20. Response bertingkat

  1. Simpan metadata dan tandai sesi untuk review.
  2. Minta revalidation launcher/module resmi.
  3. Tambahkan telemetry sementara jika confidence belum cukup.
  4. Batasi fitur kompetitif bila confidence tinggi dan kebijakan memungkinkan.
  5. Gunakan korelasi server-side dan bukti berurutan sebelum tindakan akun final.

21. False-positive checklist

  • Apakah source process bertanda tangan resmi?
  • Apakah module berada pada path resmi game/launcher?
  • Apakah operasi terjadi saat update, crash reporter, overlay, accessibility, debugger yang disetujui, atau security software?
  • Apakah target sebenarnya helper resmi, bukan game process?
  • Apakah sequence terjadi berulang dan konsisten?
  • Apakah hash/module cocok dengan allowlist build game?
  • Apakah debug-register/VEH event berasal dari modul resmi?

22. Static triage: YARA exact-match dan behavioral rules

Rule berikut ditujukan untuk defensive triage. Rule behavioral harus dikorelasikan dengan telemetry dan tidak dipakai sebagai auto-ban tunggal.

import "hash"
import "pe"

rule PBV1_Injector_Exact
{
    meta:
        description = "Exact hash of analyzed PE32 injector/controller"
        confidence = "high"
        scope = "defensive triage"
    condition:
        hash.sha256(0, filesize) ==
        "d4bda4a791062f8f4e81710370c72f9102add63c95ad12c65364a6e231a70d76"
}

rule PBV1_RuntimeDLL_Exact
{
    meta:
        description = "Exact hash of analyzed PE32 runtime DLL"
        confidence = "high"
        scope = "defensive triage"
    condition:
        hash.sha256(0, filesize) ==
        "5272468eedcdbb45662f22403916f76de738a630b75e9398c7ca9ec504b170fe"
}

rule PBV1_DisguisedINI_DLL
{
    meta:
        description = "PE32 DLL using an INI-looking filename"
        confidence = "medium"
        scope = "defensive triage"
    strings:
        $manifest = "requestedExecutionLevel" ascii
        $kernel = "KERNEL32.dll" ascii nocase
        $crt = "MSVCR100.dll" ascii nocase
    condition:
        uint16(0) == 0x5A4D and
        pe.characteristics & pe.DLL and
        filename matches /(?i)\\.ini$/ and
        $manifest and $kernel and $crt
}

rule PBV1_Injector_Behavioral_Artifacts
{
    meta:
        description = "Static indicators of analyzed remote-process injector"
        confidence = "medium"
        scope = "defensive triage; do not auto-ban alone"
    strings:
        $api_open = "OpenProcess" ascii
        $api_alloc = "VirtualAllocEx" ascii
        $api_write = "WriteProcessMemory" ascii
        $api_proc = "Process32First" ascii
        $api_next = "Process32Next" ascii
        $api_resolve = "GetProcAddress" ascii
        $target_a = "PointBl" ascii nocase
        $target_b = "pointbl" ascii nocase
    condition:
        uint16(0) == 0x5A4D and
        4 of ($api_*) and
        1 of ($target_*)
}

rule PBV1_Runtime_VEH_HardwareBreakpoint
{
    meta:
        description = "Static indicators of VEH/context-manipulation runtime module"
        confidence = "medium"
        scope = "defensive triage; corroborate with runtime telemetry"
    strings:
        $veh = "AddVectoredExceptionHandler" ascii
        $getctx = "GetThreadContext" ascii
        $setctx = "SetThreadContext" ascii
        $suspend = "SuspendThread" ascii
        $resume = "ResumeThread" ascii
        $protect = "VirtualProtect" ascii
        $flush = "FlushInstructionCache" ascii
        $debugger = "IsDebuggerPresent" ascii
    condition:
        uint16(0) == 0x5A4D and
        5 of ($veh, $getctx, $setctx, $suspend, $resume, $protect, $flush, $debugger)
}

23. Module/file triage recommendations

  • Cocokkan exact hash sebagai high-confidence IOC.
  • Verifikasi PE header, bukan ekstensi file.
  • Catat signer, path, parent process, PID, image base, load time, dan module SHA-256.
  • Bangun allowlist untuk DLL resmi agar false positive dapat ditekan.
  • Berikan risk lebih tinggi pada unsigned module dari temporary/user-writable path.
  • Jangan menyimpulkan fitur cheat tertentu hanya berdasarkan keberadaan injector/runtime artefact.

24. Server-side correlation

  • Korelasikan client telemetry dengan login/session identifier.
  • Gunakan event sequence sebagai input risk score, bukan bukti tunggal.
  • Simpan evidence sequence untuk proses appeal/review.
  • Pertimbangkan session revalidation atau competitive restriction saat confidence tinggi.
  • Korelasikan dengan anomaly gameplay bila tersedia, tetapi jangan menganggap artefak ini sendiri membuktikan fitur cheat tertentu.

25. Mitigasi dan hardening

  • Gunakan launcher resmi dan integrity validation untuk image/module.
  • Pantau external handle terhadap game dengan hak VM write/operation/create-thread.
  • Pantau context/debug-register pada titik sensitif secara selektif.
  • Validasi code page/IAT/dispatch pointer setelah initialization.
  • Korelasikan VEH registration dengan module ownership.
  • Monitor executable-writable transitions dan instruction-cache flush.
  • Pertahankan server-authoritative validation untuk state gameplay penting.
  • Jangan mengandalkan nama file, ukuran, atau satu signature saja.

26. Rencana validasi lab terisolasi

Tujuan validasi adalah membuktikan nilai runtime yang belum terlihat pada disassembly, bukan menjalankan artefak pada mesin pemain atau produksi.

Prasyarat

  • VM snapshot Windows x86/x64 tanpa kredensial produksi.
  • Salinan game/build yang disediakan developer.
  • Network sinkhole atau proxy lab yang merekam metadata.
  • Debugger/tracer yang disetujui developer.
  • Baseline build bersih tanpa artefak mencurigakan.
  • Snapshot sebelum dan sesudah setiap percobaan.

A. Baseline

Catat module resmi, thread count, memory map, VEH normal, signer, dan operasi launcher resmi selama startup. Tanpa baseline, event seperti VirtualProtect, thread creation, atau exception handler mudah disalahinterpretasikan.

B. Injector observation

  • Target process yang ditemukan.
  • Desired access pada OpenProcess.
  • Alamat dan ukuran remote allocation.
  • Jumlah/jenis remote write tanpa menyimpan data game lebih dari yang diperlukan.
  • Start address dan parameter remote thread.
  • Timing WaitForSingleObject, VirtualFreeEx, dan CloseHandle.

C. Runtime DLL observation

  • Module load dan DllMain transition.
  • Worker start addresses.
  • VEH registration dan callback ownership.
  • Thread suspend/resume.
  • Context flags dan Dr registers.
  • Protection changes dan instruction-cache flush.
  • Perbandingan seluruh event dengan baseline bersih.

D. Network observation

Catat domain/IP/port, waktu koneksi, ukuran request/response, dan parent module. Gunakan sinkhole/proxy lab; jangan mengirim kredensial produksi atau data game ke endpoint luar scope.

E. Reproducibility

Ulangi minimal tiga kali dari snapshot bersih. Pisahkan invariant behavior dari alamat/timing yang berubah akibat ASLR, build, atau scheduling.

Expected output

  • Konfirmasi primitive remote-thread final.
  • Payload path final dan hubungan antar-file.
  • Tujuan network dengan confidence yang dapat dipertanggungjawabkan.
  • Daftar event runtime yang layak diimplementasikan.
  • False-positive baseline.
  • Evidence yang cukup untuk menambah signature atau server-side rule.

Stop conditions

Hentikan eksperimen jika artefak mencoba mengakses kredensial, menyebar ke host lain, memodifikasi sistem di luar scope, atau keluar dari network sinkhole.

28. Hal yang masih belum terbukti

  • Nilai runtime final untuk seluruh placeholder dan parameter stub.
  • Nama fungsi loader final yang dipanggil remote stub.
  • Payload path final pada runtime.
  • Hubungan langsung dan urutan pemuatan ketiga artefak.
  • Tujuan network final dari seluruh request surface.
  • Apakah terdapat mekanisme hook tambahan di luar hardware-breakpoint/VEH path.

29. Metodologi dan batasan

Analisis menggunakan pemeriksaan PE, hash, import table, strings/resources, entry-point disassembly, cross-reference, dan korelasi control flow. Binary tidak dieksekusi pada workspace analisis. Karena itu, alamat loader final, parameter runtime, endpoint purpose, serta hubungan pemuatan antar-file harus divalidasi dengan debugging/telemetry terisolasi oleh pihak yang berwenang.

Beberapa jalur analisis independen digunakan untuk memeriksa ulang injector, remote stub, DLL VEH/context manipulation, modul berekstensi .ini, dan indikator defensif. Primitive utama dan hash konsisten; ketidakpastian yang tersisa sengaja dipertahankan sebagai ketidakpastian, bukan diisi dengan asumsi.

30. Kesimpulan untuk developer game

Signature perilaku paling kuat bukan nama file atau satu hash, melainkan rantai:

target discovery
  -> broad process handle
  -> remote allocation
  -> remote write
  -> remote execution
  -> runtime module activity
  -> thread suspend/context modification
  -> debug-register hardware breakpoint
  -> EXCEPTION_SINGLE_STEP
  -> VEH-based execution redirection

Untuk pertahanan yang tahan terhadap rename/rebuild, prioritas sebaiknya diberikan pada korelasi process-access telemetry, remote memory operations, remote execution, module provenance, debug-register changes, VEH ownership, dan server-side session evidence. Exact hash tetap berguna sebagai IOC cepat, tetapi behavioral sequence adalah fondasi yang lebih sulit dihilangkan tanpa mengubah arsitektur program secara signifikan.

Recommendation: gunakan IOC/hash untuk immediate triage, implementasikan sequence-based telemetry untuk detection jangka menengah, lalu lakukan isolated runtime validation untuk menutup tiga gap utama: primitive remote-thread final, payload path/relationship, dan network purpose.
