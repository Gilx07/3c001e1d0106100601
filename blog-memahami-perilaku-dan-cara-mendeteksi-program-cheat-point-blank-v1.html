Memahami Perilaku dan Cara Mendeteksi Program Cheat Point Blank V1

26 Agustus 2026Windows / PE32 / Detection Engineering

Overview

Tulisan ini membahas hasil analisis statis terhadap tiga artefak PE32 yang berkaitan dengan sebuah program cheat Point Blank V1. Fokusnya bukan pada fitur cheat di dalam game, melainkan pada perilaku teknis yang dapat diamati dan dideteksi: process discovery, remote memory operation, thread manipulation, hardware breakpoint, vectored exception handling, perubahan memory protection, dan karakteristik file yang menyamar sebagai format lain.

Ketiga artefak dianalisis tanpa dijalankan. Karena itu, setiap temuan dibedakan antara bukti statis yang kuat, hipotesis yang masih membutuhkan validasi runtime, dan indikator yang hanya layak digunakan sebagai bagian dari korelasi.

Scope: publikasi ini merupakan media riset privat untuk tujuan edukasi dan defensive analysis. Materi difokuskan pada identifikasi, telemetry, triage, mitigasi, dan false-positive handling. Detail operasional yang tidak diperlukan untuk pertahanan tidak disertakan.

Artefak yang dianalisis

Tiga file menunjukkan peran yang berbeda. Nama file sengaja tampak generik, dan salah satunya bahkan menggunakan ekstensi .ini meskipun struktur internalnya adalah DLL PE32.

Hash memberikan deteksi exact-match dengan confidence tinggi, tetapi tidak boleh menjadi satu-satunya mekanisme. Rename tidak mengubah hash, sedangkan rebuild atau modifikasi kecil dapat menghasilkan hash baru. Karena itu, hash sebaiknya menjadi lapisan pertama sebelum behavioral telemetry.

1. Executable sebagai injector/controller

Artefak executable memperlihatkan kombinasi API dan call-flow yang konsisten dengan controller yang mencari proses target, memperoleh handle dengan hak luas, mengalokasikan memory di proses lain, menulis data ke sana, lalu mengaktifkan execution primitive secara dinamis.

Import penting yang ditemukan antara lain:

CreateToolhelp32Snapshot
Process32First / Process32Next
OpenProcess
VirtualAllocEx
WriteProcessMemory
GetModuleHandleA
GetProcAddress
WaitForSingleObject
VirtualFreeEx
CloseHandle

Yang penting dari sisi detection engineering bukan satu API individual, melainkan urutan operasinya. Debugger, security software, accessibility tool, dan overlay tertentu dapat memakai salah satu API serupa secara legitimate. Confidence meningkat ketika operasi tersebut membentuk rantai yang konsisten terhadap proses game yang sama.

Analisis statis juga menemukan resolver dinamis terhadap ntdll.dll dengan signature yang sangat cocok dengan primitive pembuatan thread native. Temuan ini kuat secara statis, tetapi tetap dibedakan dari validasi runtime langsung.

2. Runtime DLL: hardware breakpoint + VEH

Artefak DLL yang lebih besar menunjukkan karakteristik berbeda. Bukti yang tersedia lebih cocok dengan custom execution redirection berbasis hardware breakpoint dan Vectored Exception Handler (VEH) daripada sekadar inline hook tradisional.

API yang relevan meliputi:

AddVectoredExceptionHandler
SuspendThread
GetThreadContext
SetThreadContext
ResumeThread
VirtualProtect
FlushInstructionCache
IsDebuggerPresent

Pada initialization, modul membuat worker thread dan memasang VEH. Salah satu callback secara khusus menangani EXCEPTION_SINGLE_STEP. Worker kemudian menginspeksi thread milik proses yang sama, menangguhkan thread, membaca context, mengubah debug registers, lalu mengembalikan context sebelum thread dilanjutkan.

Kenapa debug register penting?

Pada x86, register Dr0–Dr3 dapat menyimpan alamat hardware breakpoint, sedangkan Dr7 mengontrol aktivasi breakpoint tersebut. Pada artefak yang dianalisis ditemukan konfigurasi Dr7 = 0x55, sehingga perubahan debug register pada thread game menjadi sinyal telemetry bernilai tinggi ketika dilakukan oleh modul yang tidak resmi.

3. File .ini yang sebenarnya DLL

Artefak ketiga bernama seperti configuration file, tetapi PE header menunjukkan bahwa file tersebut adalah DLL x86. Ini adalah contoh kenapa sistem deteksi tidak boleh mempercayai ekstensi file sebagai identitas format.

Karakteristik yang ditemukan:

  • PE32 DLL x86 dengan header MZ.
  • Tidak memiliki export directory publik.
  • Import utama berasal dari KERNEL32.dll dan MSVCR100.dll.
  • Menggunakan IsDebuggerPresent dan exception filtering.
  • Memiliki operasi state berbasis InterlockedExchange / InterlockedCompareExchange.
  • Tidak menunjukkan primitive remote injection pada import table.

Penilaian yang paling aman adalah memperlakukannya sebagai runtime/guard/exception-support component yang mencurigakan, bukan langsung menyimpulkannya sebagai injector utama.

4. Detection philosophy: sequence lebih kuat daripada satu indikator

Deteksi yang hanya mencari nama file, satu API, atau satu hash mudah rapuh. Model yang lebih kuat menggabungkan static triage dan telemetry runtime.

exact/static indicator
        +
process access telemetry
        +
remote memory activity
        +
thread/context telemetry
        +
module/VEH observation
        |
        v
correlated confidence score

Sequence prioritas tinggi dalam window waktu pendek:

process discovery
  -> external OpenProcess(access luas)
  -> VirtualAllocEx
  -> WriteProcessMemory
  -> remote execution atau context modification
  -> unknown module / VEH / hardware breakpoint

5. Event telemetry minimum

Sensor client atau launcher tidak perlu merekam isi memory game untuk membangun deteksi awal. Metadata operasi sudah cukup berguna dan lebih proporsional dari sisi privacy.

{
  "timestamp": "...",
  "source_pid": 1234,
  "target_pid": 5678,
  "source_image_sha256": "...",
  "source_path_class": "user-writable|program-files|unknown",
  "operation": "open_process|remote_alloc|remote_write|remote_thread|thread_context|module_load|veh_observed",
  "requested_access": "...",
  "memory_protection": "...",
  "context_flags": "...",
  "module_sha256": "...",
  "signed": false
}

Field yang paling berguna adalah hash image, signer, klasifikasi path, source/target PID, jenis operasi, requested access, memory protection, context flags, dan timestamp. Dengan itu event dapat dikorelasikan tanpa mengambil data gameplay atau isi memory secara default.

6. Behavioral scoring

Berikut contoh baseline scoring yang dapat dipakai sebagai titik awal dan harus dikalibrasi terhadap software legitimate serta build game:

  • +100 — exact hash artefak terkonfirmasi.
  • +25 — unsigned/unknown module dengan ekstensi palsu.
  • +25 — external process membuka game dengan access luas.
  • +25 — remote allocation terhadap proses game.
  • +35 — remote write terhadap proses game.
  • +35 — remote execution primitive atau start address dari private memory.
  • +35 — suspend thread lalu Get/SetThreadContext.
  • +40 — debug register non-zero pada thread game.
  • +35 — VEH single-step dari module tidak resmi.
  • +20 — executable page berubah writable lalu executable.
  • -30 — satu sinyal tunggal berasal dari software resmi yang ditandatangani.

Interpretasi awal yang masuk akal: skor rendah hanya untuk observasi; skor menengah memicu pengumpulan telemetry tambahan; skor tinggi masuk ke investigation/containment. Auto-ban berdasarkan satu skor client tidak direkomendasikan.

7. Static triage dengan YARA

Exact hash dapat dikemas ke YARA sebagai deteksi confidence tinggi. Untuk varian yang berubah, static behavioral rule dapat menggabungkan beberapa import dan indikator PE.

import "hash"
import "pe"

rule PBV1_Exact_Injector
{
    meta:
        scope = "defensive triage"
        confidence = "high"

    condition:
        hash.sha256(0, filesize) ==
        "d4bda4a791062f8f4e81710370c72f9102add63c95ad12c65364a6e231a70d76"
}

Untuk file yang menyamar sebagai .ini, rule dapat memeriksa kombinasi header PE, flag DLL, ekstensi filename, dan string import. Pendekatan semacam ini lebih baik daripada sekadar mencari nama file karena identitas format diverifikasi dari struktur binary.

8. False-positive handling

Beberapa software legitimate dapat melakukan operasi yang mirip: debugger, overlay, crash reporter, accessibility software, endpoint security, atau tool developer. Karena itu setiap alert harus melewati checklist:

  • Apakah source process memiliki digital signature yang valid dan dikenal?
  • Apakah module berada di path resmi?
  • Apakah aktivitas terjadi bersamaan dengan update, crash handling, overlay, atau accessibility feature?
  • Apakah target benar-benar game process, bukan helper resmi?
  • Apakah sequence muncul berulang dan konsisten?
  • Apakah module/hash cocok dengan allowlist build resmi?

9. Mitigasi yang relevan

  • Validasi integritas launcher, executable, dan module resmi.
  • Bangun allowlist module berdasarkan signer, hash, dan path.
  • Korelasikan process-handle access dengan remote allocation/write.
  • Pantau perubahan thread context dan debug registers pada titik sensitif.
  • Observasi VEH yang berasal dari module tidak resmi.
  • Pantau transisi memory code menjadi writable/executable.
  • Kirim metadata evidence ke server untuk risk scoring.
  • Gunakan server-authoritative validation untuk state gameplay penting.

10. Tingkat keyakinan temuan

  • Tinggi: executable melakukan remote memory allocation/write terhadap proses lain.
  • Sangat kuat secara statis: primitive remote execution cocok dengan resolver native thread creation dari ntdll.dll.
  • Tinggi: terdapat dua jalur payload/injection pada controller.
  • Tinggi: runtime DLL memakai hardware breakpoint + VEH.
  • Rendah/tidak terbukti: runtime DLL merupakan build langsung framework hooking tertentu.
  • Rendah: file berekstensi .ini merupakan injector utama.
  • Sedang: ketiga file pasti merupakan satu paket runtime yang sama; hubungan penuh masih membutuhkan validasi runtime.

Batasan analisis

Analisis ini berbasis PE header, import table, string, hash, dan disassembly statis. Binary tidak dieksekusi. Beberapa relasi runtime—termasuk urutan pemuatan aktual dan state dinamis—masih membutuhkan validasi dalam lab terisolasi dengan logging yang terkontrol.

Kesimpulan

Signature pertahanan paling kuat bukanlah nama file tertentu, melainkan rantai perilaku: process discovery → handle luas → remote allocation/write → execution/context manipulation → unknown module/VEH/hardware breakpoint. Hash dan YARA berguna untuk exact/static triage, tetapi behavioral telemetry memberikan ketahanan yang lebih baik terhadap rename, rebuild, dan perubahan minor binary.

Untuk sistem anti-cheat yang matang, keputusan akhir sebaiknya menggabungkan telemetry client, allowlist signer/module, korelasi server-side, serta evidence sequence yang dapat diaudit. Tujuannya adalah meningkatkan confidence tanpa menjadikan satu indikator sebagai dasar hukuman otomatis.
